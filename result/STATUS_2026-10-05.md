# 페이지 캐시 작업 현황 (2026-10-05)

`STATUS_2026-10-02.md` 이후 진행한 내용이다. 코드는 모두 커밋하지 않은 상태다.

## 1. 결정 사항

- **프리페치**: 끄고 측정한다(`BENCH_PREFETCH_CACHE` 미설정). 읽기 경로는 Sirius 기본값인 O_DIRECT다.
- **TPC-H 설정**: SF50, 예산 4GB, worst 도착 순서.
  - SF50 + 6GB에서는 `small-first-big-last`가 순서를 바꾸지 않는다. 6GB를 넘는 컬럼은 `l_comment`뿐이고, 이 컬럼을 읽는 쿼리가 없다.
  - SF100 + 6GB도 시험했지만, SF50으로 가기로 했다.
- **ClickBench 설정**: 예산 6GB, natural 순서, 41개 쿼리(q28·q29 제외).
- **연구 방향 (요구사항 확장, HANDOFF에 없는 새 기법)**: 재정렬이 아는 미래 쿼리 순서를 캐시의 적재·축출에 쓴다. "재정렬이 재사용 기회를 만들고, 미래 인지 캐시가 그 재사용을 실제 히트로 이어지게 한다."

## 2. 대표 결과

조건: 프리페치 끔, O_DIRECT, 2·3회차 end-to-end wall. TPC-H는 3번 반복, ClickBench는 2번 반복.

| | ClickBench | TPC-H SF50 |
|---|---|---|
| baseline | 30.84s | 32.34s |
| paging (LRU) | 27.83s (−9.8%) | 30.86s (−4.6%) |
| paging + reorder | 26.77s (−13.2%) | 29.65s (−8.3%) |
| paging + reorder + 미래 인지 축출 | 26.66s (−13.6%) | **25.88s (−20.0%)** |

- **그림**: `headline_future.png` (스크립트 `plot_headline_future.py`), `future_cache_2x2.png` (스크립트 `plot_future_cache_2x2.py`).
- **ClickBench baseline이 38.7s에서 30.8s로 바뀐 이유**: q1 수정 때문이다(4절).

### 2×2 (원래 순서 / 재정렬 × LRU / 미래 인지)

| TPC-H (4GB, worst) | 원래 순서 | 재정렬 |
|---|---|---|
| LRU | 30.86s (−4.6%) | 29.65s (−8.3%) |
| 미래 인지, 축출만 | 29.53s (−8.7%) | 25.88s (−20.0%) |
| 미래 인지, 적재 제한 + 축출 | 28.97s (−10.4%) | 26.50s (−18.1%) |

| ClickBench (6GB, natural) | 원래 순서 | 재정렬 |
|---|---|---|
| LRU | 27.83s (−9.8%) | 26.77s (−13.2%) |
| 미래 인지, 축출만 | 27.53s (−10.7%) | 26.66s (−13.6%) |
| 미래 인지, 적재 제한 + 축출 | 27.65s (−10.3%) | 27.29s (−11.5%) |

**효과가 나는 이유 (TPC-H, 실행당)**
- 디스크 읽기(task 합): LRU 88.8s, 재정렬 + 미래 인지 73.8s (baseline 102.3s)
- 통째로 캐시에서 서빙된 batch: 8개 → 32개
- 캐시 적재 비용: 3.34s → 2.74s
- 해석: LRU는 lineitem 컬럼(각 2.2GiB)이 4GB를 돌아가며 밀어내는 상황에서, 곧 쓸 컬럼을 먼저 내보낸다. 미래 인지 축출은 다음 사용이 가까운 컬럼을 남긴다.

**ClickBench에서 효과가 작은 이유**: LRU로도 다시 쓰일 컬럼이 이미 잘 남는다. 구현 전 컬럼 단위 시뮬레이션에서도 서빙 비율이 25%에서 28%로만 올랐다.

**적재 제한이 축출만보다 못한 이유 (추정)**
- 미래 정보를 "이번 실행의 남은 쿼리"까지만 준다. 그래서 실행 끝에서 거부된 컬럼이 다음 실행 초반에 다시 쓰인다.
- 미래 범위를 실행 전체로 넓히면(1번 실행) 재정렬 + 축출이 25.88s에서 25.17s, 축출만이 29.53s에서 28.63s가 된다.

### 정확성 (미래 인지 캐시 켠 상태)

- **TPC-H** (재정렬 + 축출, 적재 제한): 3번 실행 모두 불일치 0개다. 프로세스는 `con.close()`에서 기존의 종료 시 크래시가 났다(5절).
- **ClickBench** (재정렬 + 축출, 적재 제한): 기존 동점 쿼리 9개만 다르다(26쌍, baseline과 같음).

## 3. 시도했지만 이득이 없던 것

| 시도 | 결과 | 판단 |
|---|---|---|
| 예약 양보 (`SIRIUS_PAGE_YIELD_TO_RESERVATION=1`): 메모리 예약이 막히면 캐시 페이지를 내줌 | TPC-H 재정렬 + 미래 인지 26.0s → 29.4s (+13%), LRU 31.2s → 32.0s, ClickBench 26.8s → 27.1s | 손해. 기본은 꺼 둠. 곧 쓰일 페이지를 잃는 비용이 기다리는 시간보다 크다 |
| bypass (미래 인지 모드 3): 꽉 찼을 때 다음 사용이 캐시 안의 모든 것보다 먼 컬럼은 넣지 않음 | TPC-H 26.20s → 25.91s (−1.1%, 변동 범위 안), ClickBench 26.89s → 27.34s (+1.7%) | 이득 없음. 기본은 "축출만" |
| 적재 비동기화 | 시도 안 함 | 미래 인지 적용 후 적재 비용이 task 합 2.5–3s(wall 약 0.7s)다. 원본 테이블을 batch 전달 이후까지 살려 둬야 해서 위험에 비해 이득이 작다 |

- **예약 양보 첫 버전의 오류**: 모자란 양을 용량(`get_available_memory`) 기준으로 계산해서 거의 동작하지 않았다. 예약 한도(`get_max_memory`)와 실제 할당량 기준으로 고친 뒤 위 결과를 얻었다.

## 4. 그 밖에 바뀐 것

- **ClickBench q1 (`COUNT(*)`) 수정**
  - 원인: 컬럼 목록이 비면 cuDF가 105개 컬럼을 전부 읽었다.
  - 수정: 가장 좁은 고정 너비 컬럼 하나만 읽는다(`scan_plan.cpp`, `row_count_column`).
  - 효과: 8.0s → 0.07s. 정확성은 그대로다.
- **캐시 적재 비용 재측정**: 적재 직전의 디코딩 대기는 0.01s였다. 적재 시간(task 합 3.5–3.8s)은 실제 복사 비용이다.
- **캐시 준비 시간(`stage_prep_us`) 분해**: 98%가 부분 서빙(B4)의 디스크 읽기다. 순수 비용은 0.1–0.2s다.
- **GPU 대 CPU**: GPU baseline의 45%(TPC-H), 31%(ClickBench)가 O_DIRECT 디스크 대기다. 데이터를 RAM에서 읽게 하면 GPU가 CPU 40스레드보다 빠르다. 그림 `gpu_vs_cpu_breakdown.png`.
- **TPC-H 러너 버그 수정**: `small-first-big-last`에서 `--column-bytes`를 읽지 않던 문제다. 그 결과 이 정책이 모든 컬럼 크기를 1로 보고 있었다.

## 6. 남은 일과 결정할 것

1. **미래 정보의 범위**: 기본은 "이번 실행의 남은 쿼리"다. 범위를 실행 전체로 넓히면 0.7–0.9s 더 좋아진다(1번 실행). 어느 쪽을 대표로 쓸지 정해야 한다.
2. **ClickBench의 미래 인지 효과가 작음** (−13.2%에서 −13.6%): 재정렬 + 미래 인지 조건의 두 실행이 27.23s와 26.09s로 흩어져 있어, 반복을 더 하면 결론이 분명해진다.
3. **두 벤치마크의 조건이 다름**: 예산(6GB와 4GB)과 도착 순서(natural과 worst)가 다르다. 논문에 밝혀야 한다.
4. **종료 시 크래시**: 캐시 페이지(`rmm::device_buffer`)가 메모리 풀 정리 뒤에 해제되면서 `cuMemFreeAsync`에서 난다. 결과에는 영향이 없지만 정리가 필요하다.
5. **커밋**: 여부를 정해야 한다. 커밋한다면 디버그 스위치를 빼고 기능별로 나눠서 한다.
