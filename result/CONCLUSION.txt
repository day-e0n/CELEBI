================================================================================
 페이지 캐시(CELEBI) — 결론
 ClickBench 43개, natural 순서, 캐시 예산 6GB, execution 2
================================================================================

--------------------------------------------------------------------------------
결론 한 줄
--------------------------------------------------------------------------------

  페이지 캐시는 GPU 연산 자체는 확실히 줄이지만, 그만큼 GPU 메모리를 잡아서
  태스크가 메모리를 기다리는 시간이 늘고, 응답시간은 그대로다 (-0.6%).

--------------------------------------------------------------------------------
1. 숫자
--------------------------------------------------------------------------------

| 지표                          | 캐시 없음 | 캐시 ON |    변화 |
|-----------------------------|-------|-------|-------|
| 벽시계 (사용자가 기다리는 시간)        | 76.56s | 76.14s |  -0.6% |
| Computing (겹침 제거)           | 74.12s | 74.65s |  +0.7% |
|   그중 scan                   | 45.70s | 36.19s | -20.8% |
|   그중 projection             | 28.61s | 10.46s | -63.4% |
|   그중 group by               | 53.77s | 48.24s | -10.3% |
| Reserving (메모리 예약 대기)       | 43.00s | 65.02s | +51.2% |
| Queued (큐 대기)               | 52.20s | 61.11s | +17.1% |

  연산자는 합쳐서 33초 빨라졌고, 메모리 대기가 31초 늘어 상쇄됐다.

--------------------------------------------------------------------------------

|---------------------|----|-------|
| 빨라짐 (cache hit O)   |  5 | -2.27s |

  빨라진 것                        느려진 것
    q29  -2.09s  (Referer)         q1   +0.69s  (작은 scan)

  q29 하나가 번 것을 나머지가 거의 다 까먹는다.

  q28 은 URL(9.3GB)을 읽는 쿼리인데 오히려 느려졌다. q29 는 Referer(6.8GB)를
  읽는데 빨라졌다. 같은 "큰 컬럼" 쿼리인데 방향이 반대다.

--------------------------------------------------------------------------------
3. 왜 상쇄되는가 — 측정된 사슬
--------------------------------------------------------------------------------

  (1) 캐시가 GPU 메모리 8.79GB 를 점유한다.
      예산은 6GB 로 설정했고 페이지 스토어의 회계도 6.00GB 를 지킨다
      (evicted pages=3 resident_bytes=6436511187 budget=6442450944).
      그런데 전체 드랍 시 풀 여유가 8.79GB 늘어난다. 46% 가 할당자 오버헤드다.

  (2) 가용 메모리가 17GB 에서 8.2GB 로 절반 이하가 된다.
      예약 요청의 90% 가 4.84GB 이하이므로, 받아줄 수 있는 동시 요청 수가 줄어든다.

  (3) Reserving 은 완전히 직렬이다 (합계 65.02s / 겹침제거 65.02s = 1.00배).
      태스크가 한 줄로 서서 메모리를 기다린다. 이 줄이 43 -> 65초로 길어진다.

  (4) 동시에 계산 중인 태스크가 2.85개에서 1.63개로 줄어든다.
      태스크 하나는 269.9ms 에서 153.7ms 로 빨라지는데(-43%), 동시 실행도
      같은 비율(-43%)로 줄어서 GPU 점유 시간은 그대로다.

--------------------------------------------------------------------------------
4. 캐시 안에서 일어나는 낭비
--------------------------------------------------------------------------------

  URL 페이지의 생애 (페이지 추적 원문)

      11:35:44.508  cache  URL rg0 page0        <- 적재
      11:35:44.753  evict  URL rg0 page0  pass=oversized   <- 0.25초 만에 축출
      11:35:51.883  cache  URL rg0 page0        <- 다시 적재
      11:36:08.677  evict  URL rg0 page0  pass=oversized   <- 또 축출
      11:36:54.126  cache  URL rg0 page0        <- 또
      11:37:05.762  evict  URL rg0 page0  pass=oversized   <- 또

  축출 사유가 전부 pass=oversized 다. 2단계 축출 정책의 1단계가 "컬럼 전체
  크기가 예산을 넘으면 먼저 버린다"인데, URL 은 전체 9.3GB 라 넣는 족족 1순위
  축출 대상이 된다. 그래서 적재 568장 중 483장(85%)이 축출되고 서빙은 0 이다.

  반면 SearchPhrase(2.29GB)와 UserID(1.51GB)는 축출 0건이고 넣은 것의
  291%, 410% 를 서빙한다.

  판정 기준이 틀렸다. 실제 적재 단위는 row group 이고, URL 의 row group 하나는
  864 MiB 다 (54페이지 x 16MiB). 6GB 예산에 7.1개가 들어간다. 컬럼 전체 크기
  9.3GB 로 판정하니 들어갈 수 있는 것을 못 들어가게 막고 있다.

--------------------------------------------------------------------------------
5. 재정렬 (small-first-big-last)
--------------------------------------------------------------------------------

  도착 순서 5종에서 평균 +7.2% (개선 2 / 악화 3). 이득이 아니다.

  근본 한계: ClickBench 총시간의 72% 를 q28, q29 둘이 쓴다. 나머지 41개는
  어떤 순서로 돌려도 20초 안쪽이다. 재정렬이 움직일 수 있는 폭이 애초에 작다.

  TPC-H 에서는 기본 설정으로 순서를 아예 바꾸지 않는다 (예산을 넘는 컬럼이
  하나도 없어서). 임계값을 낮춰 동작시키면 도착 순서 5종에서 +2.1%, 노이즈 안.

--------------------------------------------------------------------------------
6. 이 결론에 이르기까지 틀렸던 것들
--------------------------------------------------------------------------------

  [1] 지표를 잘못 썼다 — 가장 큰 실수
      "GPU 연산자 시간 합"을 총시간으로 쓰고 모든 백분율을 거기서 냈다.
      이 값은 동시에 도는 태스크들의 시간을 중복해서 더한다 (ClickBench 에서
      2.85배). 캐시를 켜면 중복이 줄어 합계가 -37% 가 되지만 벽시계는 -0.6%
      다. CLAUDE.md 에 "total_ms 는 GPU 연산자 시간의 합이지 벽시계가 아니다"
      라고 적혀 있었는데 그 경고를 흘렸다.
      -> 이 지표로 낸 모든 수치(캐시 -37.2%, 재정렬 -15.3%, 정책 9개 비교)는
         응답시간 개선으로 읽을 수 없다. 태스크 단위 작업량으로는 유효하다.

  [2] "큰 컬럼 적재가 순손실" — 기각
      URL 서빙이 0 이므로 적재가 낭비라고 보고 SKIP_OVERSIZED 로 막아봤더니
      scan 이 47.91 -> 73.07s 로 악화됐다. serve 로그는 "row group 의 페이지가
      전부 있을 때"만 찍히므로 큰 컬럼에 대해 구조적으로 0 을 낸다.

  [3] "downgrade 가 작업을 GPU 밖으로 내린다" — 틀림
      로그를 보니 0바이트, 240KB, 478KB 만 반환한다. 아무것도 안 내려간다.
      이건 내 메모리에 "memory-pressure sweep frees 0 bytes" 로 이미 있던
      사실인데 잊고 새 설명을 지어냈다.

  [4] "캐시가 병렬 태스크 수를 줄인다" — 틀림
      태스크 수는 1503 vs 1512 로 같다. 줄어든 것은 동시 실행 수(2.85 -> 1.63)
      이지 태스크 수가 아니다.

  [5] "URL row group 하나가 3.7GB" — 집계 오류
      같은 페이지가 축출-재적재로 4번 찍히는 것을 합산했다. 실제는 864 MiB 고,
      6GB 에 1.7개가 아니라 7.1개가 들어간다.

  [6] 캐시를 끈 채로 재고 "재정렬이 2.6배 느리다"고 보고
      러너는 BENCH_PREFETCH_CACHE=1 이 있어야 캐시를 켜는데 스크립트가 그걸
      주지 않았다. 대조군이 77~83초(캐시 켠 같은 순서는 28.9초)로 나온 것이
      이상해서 설정을 비교하다 잡았다.

  [7] 간트 차트에서 "CELEBI 가 q29 를 8.3초 빠르게 끝낸다"
      그 그림은 q29 의 태스크 24개 중 긴 6개만 그린 것이었다. 전체로는 2.09초다.

--------------------------------------------------------------------------------
7. 다음에 할 일 (근거가 있는 것만)
--------------------------------------------------------------------------------

  1) 축출 판정을 컬럼 전체 크기가 아니라 row group 크기로 바꾼다.
     URL 은 row group 864 MiB 라 상주 가능한데 지금은 9.3GB 로 판정돼 1순위로
     버려진다. 넣자마자 버리는 사이클이 사라지면 적재 35.33 GiB -> 8.8 GiB.

  2) 캐시의 실제 메모리 점유를 회계와 맞춘다.
     회계 6.00GB, 실제 8.79GB. 46% 차이가 Reserving 대기를 만든다.

  3) 그 다음에 캐시가 벽시계로 이득을 내는지 다시 잰다.
     Computing 에서 33초를 버는 것은 이미 측정됐다. 메모리 점유만 줄이면
     그 33초가 응답시간으로 넘어올 여지가 있다.

  4) 재정렬은 3)이 성립한 뒤에 본다. 지금은 키울 이득이 없다.
