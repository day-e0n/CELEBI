# 페이지 캐시 작업 현황 (2026-10-02)

`result/HANDOFF.md`의 요구사항 기준으로, 이번 작업에서 바뀐 것과 측정 결과를 정리한다.
코드는 모두 커밋하지 않은 상태다.

## 1. 요구사항별 상태

| | 요구 | 상태 |
|---|---|---|
| B1 | 16MB 페이지 단위 | 유지 |
| B2 | offset 기준으로 자르기 | 유지. 문자열은 offsets를 호스트로 읽어 "16MB를 넘지 않는 마지막 행"에서 자른다 |
| B3 | 16MB 안 되면 더미로 채워 16MB | **완료.** 모든 페이지가 정확히 16MiB 할당 하나(데이터, mask, offsets를 그 안에 배치). 더미 비율은 fixed-width 18.4%, variable-width 2.3%이며 전부 row group 끝 조각에서 나온다 |
| B4 | row group의 페이지가 전부 없어도 사용 | **완료.** 있는 페이지는 캐시에서 쓰고 빠진 행 구간만 디스크에서 읽는다(파일 전체 기준 행 번호, row group 지정 없이). `SIRIUS_PAGE_PARTIAL_SERVE=0`으로 끈다 |
| B5 | fixed·variable 하나의 예산 | 유지. 서빙하지 않던 pinned entry 저장소 적재를 꺼서 예산 안에 페이지 저장소만 남음 |
| B6 | 너무 큰 컬럼 안 올리기 | 지금 코드로 다시 측정. 효과가 변동 범위 안이라 기본은 꺼 둔 채 유지(기각 유지) |
| B7 | variable 먼저 축출 | **요구대로 수정.** 이전 코드는 "컬럼 전체가 예산보다 크면 먼저"라는 다른 기준이었다. `SIRIUS_PAGE_EVICT_ORDER=size`로 이전 기준 비교 가능 |
| R1 | 설정한 예산만큼만 사용 | 모든 실행에서 최대 6.00GiB |
| R2 | OOM 없음 | 모든 실행에서 0회 |
| R3 | 성능이 확실하게 개선 | 프리페치 OFF에서는 달성, HANDOFF 설정(프리페치 ON)에서는 작음. 아래 3절 |
| C1–C3 | 세 조건, 두 벤치마크, natural 순서 | 3절 표 |
| C6 | 정확성 | 프리페치 OFF에서 TPC-H 22×3 일치, ClickBench는 기존 동점 9개만 다름 |

## 2. 코드 변경 (커밋 안 함)

- 컬럼이 전부 캐시에 있을 때 디스크를 읽지 않고 캐시로 서빙(이전에는 버리고 디스크에서 다시 읽었음).
- 문자열 컬럼만 있는 batch도 페이지 저장소에 넣음(이전에는 입구에서 거절). `SIRIUS_PAGE_STORE_STRING_ONLY=0`으로 되돌림.
- **필터 전 캐싱 기본 ON**(`SIRIUS_FIXED_PAGE_CACHE_BEFORE_FILTER`, 끄려면 `=0`). 필터 있는 쿼리도 필터 없이 저장된 페이지를 쓰고 필터는 다음 단계에서 적용한다. 캐시 서빙 비율(요청 바이트 기준)을 5.7%에서 13–15%로 올린 가장 큰 변화.
- 16MiB 고정 페이지(B3), 부분 서빙(B4), variable 먼저 축출(B7).
- 페이지 경계를 null mask 유무와 무관하게 자르고, run 행 수 검증 추가. 이 버그로 q33이 `Column size mismatch: 30493568 != 30000000`로 실패한 적이 있다.
- 적재 비용 줄이기: 페이지당 이중 복사 제거, 쓰이지 않던 페이지별 최소/최대 통계 계산 제거, null 개수와 문자열 경계 동기화를 row group당 한 번으로.
- `_pinned_entries` 데이터 레이스 수정(락 순서 pinned → pages).
- 계측: `SIRIUS_SCAN_CACHE_TRACE=1`(스캔 × 컬럼 캐시 상태), `[scan-populate]`, `[scan-stage]`, `full_hit`, `partial_serve`.
- 임시 디버그 스위치(커밋 금지): `SIRIUS_PREFETCH_DBG_*` 6개.

## 3. 최종 측정 (C1, C2)

3회 실행 중 2·3회차 평균, 6GB 예산, min_free 6GB, natural 순서, ClickBench는 q28·q29 제외.

| 조건 | TPC-H SF50 | ClickBench |
|---|---|---|
| 프리페치 ON: baseline | 11.31s | 18.83s |
| 프리페치 ON: 캐시 | 11.26s (−0.4%) | 18.28s (−2.9%) |
| 프리페치 ON: 캐시 + 재정렬 | 11.16s (−1.3%) | 18.40s (−2.3%) |
| 프리페치 OFF: baseline | 32.04s | 38.69s |
| 프리페치 OFF: 캐시 | 26.14s (−18.4%) | 35.83s (−7.4%) |
| 프리페치 OFF: 캐시 + 재정렬 | 26.23s (−18.1%) | 34.28s (−11.4%) |

- TPC-H는 재정렬이 실제 실행 순서를 바꾸지 않는 것을 확인했다. 그래서 TPC-H의 캐시 대 재정렬 차이는 실행 간 변동(약 1%)이다.
- 프리페치를 켜면 baseline 자체가 절반으로 빨라져, 캐시가 줄일 디스크 읽기 몫이 작아진다.

## 4. 남은 문제

1. **I/O 프리페치 캐시 버그**: `BENCH_PREFETCH_CACHE=1`에서 TPC-H가 캐시와 무관하게 행을 잃는다(q4, q5, q10, q12). 디바이스 읽기 캐시 히트에서 행이 빠진다는 것까지 확인했고 원인 코드는 미확정이다. HANDOFF의 실험 설정은 이 옵션을 켠다.
2. **R3(프리페치 ON)**: 이득이 0.4–2.9%로 작다. 남은 큰 손실은 적재 거부(min_free 때문, 요청 바이트의 44%)와 캐시보다 큰 문자열 컬럼(URL, Title)이다.
3. **재정렬 A5**: `small-first-big-last`에 A5(동점 규칙)가 들어가 있지 않다. HANDOFF 지시대로 R3 전에는 손대지 않았다.
4. q28·q29: HANDOFF의 실행 명령을 따라 제외했다(C5와 충돌 여부 확인 필요).
